# Northbeam CRM — Project Context

This document is a complete handoff of the current state of this project, written
so an LLM with no prior access to the repository can understand what exists,
why it's built the way it is, and what to do with it next. It covers
architecture, domain model, business rules, and conventions — not a
line-by-line restatement of the source (read the actual files for that).

## 1. What this project is

**Northbeam CRM** — a lead management and sales automation CRM. It covers:
leads (pipeline/stages), tasks, meetings, proposals, and multi-step
automation **workflows** (email/WhatsApp sequences run by an external
automation engine, n8n) with **runs** (per-lead workflow executions) and
**templates** (the messages those workflows send).

**Current state: frontend only, mock data, no backend.** The entire app runs
against deterministic in-memory data seeded on load and reset on refresh.
There is no Supabase, no n8n, no auth, no real API calls anywhere. The data
shapes and the module boundaries were deliberately designed as the future
integration contract (see §7 "Backend integration seams") — the intent
baked into the code (via comments) is: plug a real backend in behind the
existing `src/store` hooks without changing any UI component.

Only `Frontend/` exists in this repo. There is no backend service/repo yet.

### Recent architecture change (important context)

This app **was** built on TanStack Start (SSR, file-based routing +
server functions) with Nitro producing a Node server (`.output/`). It was
**migrated to a plain client-side SPA** because:
- No server functions / server-only code were ever actually used (verified:
  no `createServerFn`, `createServerOnlyFn` anywhere in the codebase) — the
  SSR layer added zero real backend functionality, only SSR-error-page
  plumbing.
- The target production shape is: `Vite build → dist/ → Nginx static
  hosting → Docker`, with a separate backend service to be added later.

What changed in that migration (so it isn't re-introduced by mistake):
- Removed: `@tanstack/react-start`, `nitro`, `src/server.ts`, `src/start.ts`,
  `src/lib/error-capture.ts`, `src/lib/error-page.ts`.
- Added: `index.html` (standard Vite entry) and `src/main.tsx`
  (`createRoot` + `RouterProvider`, no SSR).
- `vite.config.ts` now uses `@tanstack/router-plugin`'s `tanstackRouter()`
  plugin directly (just for file-based route codegen), not the Start plugin.
- `src/routes/__root.tsx` lost `shellComponent`/`<Scripts />` (SSR-only
  APIs) but **kept** `<HeadContent />` and each route's `head()` config —
  those work fine client-side for managing `<title>`/meta tags per route.
- Build now outputs `dist/`, not `.output/`. `npm start` no longer exists;
  there's no Node server in production — Nginx serves the static files with
  SPA fallback (`try_files $uri $uri/ /index.html`) so deep-link refreshes
  (e.g. `/leads/l1`) work.
- `Dockerfile` is now multi-stage: `node:22-bookworm-slim` build stage →
  `nginxinc/nginx-unprivileged:1.27-alpine` runtime stage (non-root, port
  8080), with `nginx.conf` alongside it.

**Do not** reintroduce TanStack Start, Nitro, or any SSR mechanism unless
a real requirement for server-rendering appears — the app is intentionally
a pure CSR SPA now.

layout is `routes/__root.tsx` (wraps every page in `<AppShell>`, provides

hand-edit `routeTree.gen.ts` — it's regenerated by the router plugin from
the files in `routes/`.

| `routes/tasks.tsx` | `/tasks` | `TasksPage` |

## 5. State management architecture

**No Redux/Zustand/Jotai.** State is plain React `useState` inside
custom hooks ("slices"), each exposed through its own React Context so a
component subscribing to e.g. `useTasks()` doesn't re-render when leads
change. `StoreProvider` (in `store/store-provider.tsx`) composes all eight
slices in dependency order and nests their providers. It's mounted once, in
`routes/__root.tsx`.

### 5.1 Public API (`import { ... } from "@/store"`)

| Hook | Returns |
|---|---|
| `useLeads()` | `{ leads, getLead, addLead, updateLead, setNextAction, setAutomation, markDnc, addNote }` |
| `useTasks()` | `{ tasks, addTask, toggleTask }` |
| `useMeetings()` | `{ meetings, addMeeting, updateMeeting }` |
| `useProposals()` | `{ proposals, addProposal, updateProposal }` |
| `useAutomations()` | `{ workflows, runs, templates, templateName, updateWorkflow, updateDraftSteps, createDraft, publishVersion, duplicateWorkflow, updateRun, addTemplate, updateTemplate }` |
| `useSession()` | `{ users, currentUser, userName }` (static directory + signed-in user; no real auth) |
| `useNotifications()` | `{ notifications, markNotificationsRead }` |
| `useTimeline()` | `{ timeline, addTimeline }` — the cross-domain audit log every other slice writes to |

Components **only** ever import from `@/store`, never reach into
`src/mocks/seed` or a slice's internals directly. This is the explicit
integration seam: **swapping the mock-backed implementation of one
`use*Slice` for a React Query hook against a real API changes only that
one file** — every consuming component keeps working unchanged, because
the returned shape stays the same.

### 5.2 Cross-slice wiring

- `useIdFactory()` (`store/ids.ts`) mints ids (`l1001`, `tk1002`, `mt1003`,
  …) scoped to the provider instance (not module-level — avoids leaking
  counters across renders/tests).
- The **timeline** is the shared audit trail: every mutating action in
  every other slice (leads, tasks, meetings, proposals, automations) also
  calls `addTimeline(...)`. This is what powers the lead detail page's
  "Activity" tab.
- Leads and automations are cross-wired via `RunEffects`
  (`applyAutomationMode`, `cancelRunsForLead`) — pausing a lead's
  automation or marking it Do Not Contact updates the matching `runs`
  records (workflow executions) so the UI reflects that automation
  actually stopped.

### 5.3 Fixed clock

`mocks/seed/clock.ts` defines `TODAY = "2026-08-26"` — the entire seed
dataset is authored as offsets from this fixed date so "Today" / "Overdue"
/ relative labels stay meaningful without drifting as real time passes.
`lib/dates.ts`'s `NOW` constant (`${TODAY}T12:00:00`) is what gets written
onto records the user edits during a session. **When a real backend
replaces the seed, `NOW` becomes `new Date().toISOString()` and this whole
fixed-clock mechanism is deleted** (this is called out explicitly in code
comments).

### 5.4 Seed data volume

Small, hand-authored fixture set: ~14 leads, 4 users, 14 tasks, 8 meetings,
5 proposals, several workflows (with multiple versions/steps each), 9
workflow runs, 6 templates, 40 timeline events, 5 notifications.

### 6.2 Business rules — this is what a converting LLM must not lose

**Log Call → outcome routing** (`features/leads/log-call-dialog.tsx`):

| Outcome | Stage → | Automation → | Task created |
|---|---|---|---|
| Not connected | `Not Connected Nurture` | `Active` | Call retry, +2 days |
| Positive | `Meeting Scheduling` | `Manual` | Schedule discovery meeting, +1 day |
| Maybe | `Maybe Nurture` | `Active` | Follow-up after nurture email, +7 days |
| Negative | `Negative Nurture` | `Active` | Long-term re-engagement check, +30 days |
| Callback Requested | (unchanged) | `Manual` | Callback task, due on user-picked date |
| Do Not Contact | → `markDnc()`: stage untouched but `doNotContact=true`, `automation=Stopped`, all runs for that lead cancelled, `nextAction` cleared | | |

**Meeting outcome routing** (`features/meetings/meetings-page.tsx`):
- `Proposal Required` → stage `Proposal Preparation`, task "Prepare and upload proposal" +2 days
- `Not Interested` → stage `Long-Term Nurture`, task +45 days
- `Follow-up Required` / `Second Meeting` → stage `Meeting Scheduling`, task type `Schedule Meeting` +3 days

**Proposal status routing** (`features/proposals/proposals-page.tsx`):
- `Sent`/`Pending` → stage `Proposal Pending`, next action "Follow up on proposal" +3 days; `Sent` also stamps `sentDate`/`followUpDate`
- `Accepted` → stage `Won`, `nextAction: null`, `automation: Stopped`
- `Rejected` → stage `Long-Term Nurture`, next action +45 days

**Workflow versioning** (`features/automations/workflow-builder-page.tsx`,
slice `automations.ts`):
- A workflow has multiple `versions[]`, each with its own `steps[]` and a
  `status` of `Draft | Published | Previous`.
- Only one version is ever "Draft" at a time per workflow (`createDraft`
  returns the existing draft if one exists, otherwise clones the currently
  published version's steps into a new version number).
- Only a `Draft` version is editable (add/remove/reorder steps, toggle
  enabled, edit delay/action/template/config) — a `Published`/`Previous`
  version is read-only in the UI.
- `publishVersion` flips the target version to `Published`, demotes the
  previously-published version to `Previous`, and sets `currentVersion` on
  the workflow.
- Publishing shows an "enrollment mode" choice dialog (continue on old
  version / migrate to same step on new version / restart from step 1) —
  **this choice is currently UI-only and not wired to any real effect**
  (no run migration logic exists yet — worth flagging to whoever wires the
  real backend).
- Steps: each has `delayDays`, an `action` (`Send Email` / `Send WhatsApp`
  / `Create Call Task` / `Create Follow-up Task` / `Change Lead Stage` /
  `Stop Workflow`), and depending on the action either a `templateId`
  (email/WhatsApp) or a free-text `config` (stage name / task title / note).

**Runs page**: shows per-lead workflow executions; Failed runs can be
retried, Running/Waiting runs can be paused, Paused runs can be resumed.
Static informational copy on the page states the intended real behavior:
"Before every step n8n re-checks the lead: still active, not suppressed, no
newer reply and no meeting booked. If any check fails the run is cancelled
instead of sending" — **this check does not actually exist in the mock
layer**, it's documentation of intended backend behavior.

**Add Lead**: requires first name + company + (email or phone). New leads
always start at stage `New`, automation `Manual`. On save, navigates to the
new lead's detail page.

**Dashboard**: aggregates counts across all slices — active leads (not
closed, not DNC), tasks due today/overdue, meetings today, proposals in
`Sent`/`Pending`, leads with no next action — plus a simple pipeline funnel
(Leads → Called → Connected → Meetings → Proposals → Won) computed by
scanning the shared `timeline` for `call`/`Call Connected` events.

## 7. Backend integration seams (explicit, from code comments)

The codebase was deliberately written expecting **Supabase** (data/auth)
and **n8n** (workflow execution engine) as the eventual backend, though
neither is wired up yet:
- `src/types/index.ts`: domain types are "the contract the backend will
  have to satisfy... Supabase-generated row types should be mapped into
  the domain contracts in `src/types` instead of being imported directly
  by UI components."
- `src/store/index.ts`: "Backend swap point: each `use*Slice` in
  `./slices` seeds itself from `src/mocks/seed`. Replacing one with a React
  Query hook against the API changes only that file — the hooks below keep
  the same shape, so no component has to change."
- Multiple UI strings say things like *"UI changes are stored in Supabase
  and picked up by n8n"* (lead detail page), *"Publishing writes the new
  sequence to Supabase; n8n reads it on the next scheduled run"* (workflow
  builder), *"Automation runs in n8n and is controlled from here"* (lead
  detail automation tab).
- `TanStack Query` (`@tanstack/react-query`) is already installed and a
  `QueryClient` is already provided at the router/root level
  (`router.tsx`, `__root.tsx`) — it's just not used by any slice yet. This
  is clearly the intended mechanism for the real data-fetching layer once
  a backend exists.
- `src/store/ids.ts` and `src/mocks/seed/clock.ts` both have comments
  explicitly saying they exist only until a real backend owns id
  generation and timestamps, respectively — delete them at that point.

**If asked to "wire up a backend" or "convert to use real data"**: the
correct approach given this architecture is to keep every component and
every `types/*.ts` shape unchanged, and rewrite the *implementations*
inside `store/slices/*.ts` (state + mutations) to call a real API /
Supabase client / React Query hooks instead of `useState(seed.x)`, keeping
each slice's returned hook shape identical.

## 8. UI / design system conventions

- shadcn/ui, `"new-york"` style, `baseColor: "slate"`, CSS variables for
  theming (`components.json`). Radix primitives underneath every
  interactive component in `components/ui/`.
- Icons: `lucide-react` exclusively.
- Toasts: `sonner`'s `toast.success(...)` called after nearly every mutating
  action — this is the app's primary "did that work" feedback mechanism, not
  inline banners.
- `<StatusBadge value tone? dot? />` (`components/common/status-badge.tsx`)
  is the single place status-like strings become colored pills. It has a
  hardcoded `value → tone` lookup covering every pipeline stage, automation
  mode, run status, meeting status, and proposal status; falls back to
  `"neutral"` for unknown values, or an explicit `tone` prop can override.
  Seven tones: `neutral, info, success, warning, danger, primary, muted`.
- Layout: `<AppShell>` (`app/app-shell.tsx`) is the persistent chrome
  (sidebar with nav + "Add Lead" button, top header with search-as-you-type
  lead lookup, notification bell popover, ⌘K/Ctrl+K command palette via
  `cmdk`). `<PageHeader title description? actions? tabs? />` is the
  shared per-page header bar used by every feature page.
- Fonts: Geist / Geist Mono, loaded from Google Fonts in each route's
  `head()` links.
- Tables are the dominant list UI (leads, tasks, meetings, proposals,
  runs) — plain `<table>` with `overflow-x-auto` wrappers, not a data-grid
  library.
- Currency formatting is India-specific: `money()` in `lib/format.ts`
  renders ₹ with Lakh/Crore abbreviations (`₹4.5 L`, `₹1.20 Cr`).

## 11. Known gaps / things a converting LLM should ask about, not assume

- No auth of any kind — `useSession()` just returns a static seeded user.
- No real API/network layer — TanStack Query is installed but unused.
- Publish "enrollment mode" (continue/migrate/restart) in the workflow
  builder is UI-only, not implemented.
- n8n's described pre-send safety checks (still active / not suppressed /
  no newer reply / no meeting booked) are documentation of intent only —
  not implemented in the mock runs data.
- File upload for proposals is a text-field stand-in (`fileName` string),
  not an actual file upload.
- No pagination anywhere — all lists render the full (small) seeded array.
- No environment-variable-driven config yet (no `.env.example`); if a
  backend URL is introduced, use the `VITE_` prefix convention and keep
  secrets out of frontend env entirely.
